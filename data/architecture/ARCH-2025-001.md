# Payment Platform Resilience Architecture

Document ID: ARCH-2025-001
Department: Engineering
Document type: Architecture
Access level: Internal
Created date: 2025-01-22

## Purpose and Scope

This document describes the target resilience architecture for payment authorization and settlement services. It covers synchronous authorization, asynchronous settlement, operational controls, data consistency, security boundaries, recovery objectives, and observability. Merchant-specific integrations and card-scheme certification details are outside this document.

## Architecture Goals

- Maintain authorization availability during a single availability-zone failure.
- Prevent retries from amplifying downstream degradation.
- Preserve exactly-once financial effects while allowing at-least-once message delivery.
- Recover queued settlement work without changing the original business date.
- Enforce service identity, least privilege, encryption, and auditable configuration changes.
- Give operations enough signals to distinguish demand spikes, dependency failures, and database saturation.

## System Context

Customers and merchants submit payment requests through Mobile Banking, Internet Banking, or Merchant API ingress. The API Gateway authenticates callers and forwards validated requests to the Payment Authorization service. Authorization uses the Gateway Adapter to communicate with external payment networks and writes an immutable audit result. Successful authorizations publish settlement and notification events.

Settlement Processing consumes settlement events, enriches them with ledger and merchant data, and produces settlement instructions. Notification Dispatcher independently consumes payment-state events. Notification failure cannot change the payment outcome.

## Main Components

| Component | Responsibility | Scaling model |
|---|---|---|
| API Gateway | Authentication, rate limiting, request validation, correlation IDs | Horizontally scaled across two zones |
| Payment Authorization | Idempotency, payment validation, orchestration, response mapping | Stateless replicas with minimum three per zone |
| Gateway Adapter | Network-specific protocol and bounded retry handling | Stateless replicas partitioned by provider |
| Authorization Audit database | Durable authorization decisions and idempotency records | Multi-zone primary with synchronous standby |
| Event Broker | Durable settlement and notification events | Three-node quorum across zones |
| Settlement Processing | Ledger enrichment, batching, settlement instruction creation | Queue-based workers with controlled autoscaling |
| Notification Dispatcher | Push, SMS, and email delivery | Independent queue consumers |
| Runtime Configuration service | Audited pool limits, retry budgets, and feature flags | Multi-zone replicated service |

## Authorization Data Flow

1. API Gateway verifies the caller and creates a correlation ID.
2. Payment Authorization validates amount, currency, account state, and idempotency key.
3. The service reads or creates an authorization audit record.
4. Gateway Adapter sends one primary request to the selected payment network.
5. Transient failures may use the configured retry budget; permanent declines are never retried.
6. The final decision is written to the audit database before the response is returned.
7. Successful decisions publish `payment.authorized.v1` using an outbox record.
8. Settlement and notification consumers process the event independently.

## Reliability Model

Application replicas are distributed across two availability zones. Zone-aware routing keeps at least 40% spare capacity in each zone so one zone can absorb essential traffic from the other. Circuit breakers isolate a degrading gateway, while bulkheads prevent one merchant or provider from consuming every worker.

Every caller uses exponential backoff with full jitter. The standard authorization retry budget is two retries within 1.5 seconds. Retries require an unchanged idempotency key. A global retry limiter rejects excess retries before they reach database or gateway dependencies.

Settlement and notification flows use durable queues. Consumers acknowledge messages only after their durable state change completes. Dead-letter queues retain messages that exceed the bounded processing-attempt limit.

## Data Consistency and Idempotency

The authorization idempotency key is unique within a merchant and 24-hour window. Repeated requests with the same key and matching payload return the stored decision. A reused key with a different amount, currency, or beneficiary is rejected.

An outbox table couples the authorization decision and event publication intent in one database transaction. A publisher sends unsent records to the broker and marks them published. Consumers maintain their own processed-event ledger, so duplicate broker delivery does not create duplicate financial effects.

## Capacity Controls

Each Payment Authorization replica has a database pool of 180 connections, including a 20-connection administrative reserve. Autoscaling considers request rate, connection wait time, and CPU. It does not scale solely on CPU because database waits can occur while CPU remains low.

Capacity tests must cover forecast peak plus 100% headroom, one-zone loss, gateway latency of two seconds, and retry behavior. Releases fail the capacity gate if pool utilization exceeds 75%, p95 connection wait exceeds 100 milliseconds, or retry volume exceeds 15% of primary requests.

## Security Controls

- Mutual TLS authenticates service-to-service traffic.
- Workload identities receive narrowly scoped database and broker permissions.
- Payment data is encrypted in transit and at rest using managed keys.
- Logs exclude full account numbers, authentication secrets, and message bodies.
- Runtime configuration changes require an approved change reference and produce an audit event.
- Administrative pool reserves are accessible only to the database operations role.

## Observability

Every request carries a correlation ID across gateway, authorization, adapter, database, and event publication. Required metrics include authorization success, gateway latency, retry ratio, circuit-breaker state, active and waiting database connections, outbox age, settlement queue age, dead-letter volume, and consumer drain rate.

Alerts use service outcomes and saturation indicators. Authorization success below 99.5% for two minutes is critical. Pool utilization above 80% for two minutes is warning; above 90% for one minute is critical. Settlement queue age above 15 minutes is warning and above 30 minutes is critical.

## Recovery Objectives

| Capability | Recovery time objective | Recovery point objective |
|---|---:|---:|
| Payment Authorization | 15 minutes | 0 committed decisions |
| Authorization Audit database | 30 minutes | 0 committed transactions |
| Settlement Processing | 60 minutes | 0 acknowledged events |
| Notification delivery | 4 hours | 0 acknowledged events |

## Failure Modes and Responses

| Failure mode | Expected automated response | Operator action |
|---|---|---|
| Gateway latency | Open circuit after threshold and use bounded retry | Confirm provider status and traffic policy |
| Database pool saturation | Reject excess work, reduce retry concurrency | Follow RUN-2025-001 and assess pool headroom |
| Event broker partition | Continue authorization with local outbox buffering | Monitor outbox age and broker quorum |
| Settlement backlog | Controlled worker scaling | Follow RUN-2025-002 and reconcile totals |
| Notification provider outage | Queue events and use alternate channel where allowed | Follow RUN-2025-003 |

## Architecture Decisions

The platform uses a modular service architecture with durable events because authorization latency and settlement throughput have different scaling and recovery needs. The outbox pattern was selected over distributed transactions to preserve local atomicity while allowing asynchronous delivery. Runtime controls are audited because changing retry or pool limits can affect system safety as strongly as a code release.

## Ownership

Payments Platform owns authorization and settlement application recovery. Site Reliability owns shared alerting, incident coordination, and traffic management. Database Engineering owns audit-database availability and plan governance. Security Engineering owns workload identity and key-management standards.
