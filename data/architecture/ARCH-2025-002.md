# Event-Driven Payment Notification Architecture

Document ID: ARCH-2025-002
Department: Engineering
Document type: Architecture
Access level: Internal
Created date: 2025-06-25

## Purpose

This document defines the architecture for sending payment confirmations and status updates through push, SMS, and email. Notification delivery is asynchronous and cannot determine, reverse, or retry a payment outcome.

## Design Principles

- The payment ledger is the source of truth for payment state.
- Delivery is at least once, with idempotent handling at every consumer and provider boundary.
- Channel failure is isolated from authorization and settlement.
- Message content contains the minimum data needed for the selected template.
- Customer preferences and regulatory restrictions are checked before delivery.

## Components

| Component | Responsibility |
|---|---|
| Payment Event Topic | Durable authorized, declined, settled, and reversed events |
| Notification Router | Selects eligible channels using customer preferences and event type |
| Template Renderer | Produces locale-specific content from approved templates |
| Notification Queue | Buffers delivery jobs and supports delayed retries |
| Notification Dispatcher | Sends jobs to push, SMS, or email providers |
| Delivery Ledger | Records channel, provider request ID, idempotency key, and delivery status |
| Dead-Letter Queue | Stores jobs that exceeded the retry policy |

## Event Contract

The input event includes `event_id`, `event_type`, `payment_id`, `occurred_at`, `amount`, `currency`, `customer_reference`, and `schema_version`. Full account numbers, card numbers, authentication data, and provider credentials are prohibited.

The `event_id` is globally unique and becomes the base notification idempotency key. A separate job ID is created per eligible channel. Consumers reject unsupported schema versions and route malformed events to quarantine.

## Delivery Flow

1. Notification Router receives a payment-state event.
2. It checks customer preferences, legal restrictions, and channel availability.
3. Template Renderer creates content using the approved event-type template.
4. A channel-specific job is written to Notification Queue.
5. Notification Dispatcher checks Delivery Ledger for an existing successful result.
6. The provider request includes the channel job ID as its idempotency key.
7. Provider response is recorded before the queue message is acknowledged.
8. Failed transient jobs are delayed using exponential backoff with jitter.

## Retry and Dead-Letter Policy

Transient provider errors use delays of 30 seconds, two minutes, ten minutes, and thirty minutes. Rate-limit responses honor the provider's retry-after value within the four-hour delivery objective. Permanent errors such as invalid destination, blocked recipient, or rejected template are not retried.

After five unsuccessful attempts, the job enters the dead-letter queue with a reason code. Replaying a job preserves the original job ID so provider idempotency remains effective.

## Availability and Capacity

The router and dispatcher run in two availability zones. Queues are replicated across three broker nodes. Normal volume is 180 messages per second, forecast peak is 600 per second, and tested capacity is 1,200 per second. The queue must absorb four hours of peak events without data loss.

Dispatcher autoscaling uses ready-job count, oldest-job age, provider latency, and provider rate limits. Scaling cannot exceed provider-approved request quotas.

## Security and Privacy

Templates receive masked payment references and the minimum necessary amount and currency. Destination addresses are retrieved by a trusted delivery service and are not written into general application logs. Provider credentials come from the secret manager and rotate every 90 days.

Delivery Ledger retains operational metadata for 90 days. Message bodies are retained for seven days for delivery troubleshooting and are accessible only to the Customer Communications operations role.

## Observability

Required metrics include event intake rate, routing exclusions, queue age, delivery latency, provider success rate, retry count, duplicate-suppression count, and dead-letter volume. Alerts fire when p99 enqueue-to-provider time exceeds 60 seconds, duplicate ratio exceeds 0.05%, or any dead-letter queue gains more than 100 items in ten minutes.

## Failure Isolation

A provider outage opens a channel-specific circuit breaker and leaves jobs queued. Other channels continue if customer preference permits. Template or preference-service failures stop the affected job before provider submission. Analytics failures never block queue acknowledgment or successful delivery-state recording.

## Deployment Strategy

Dispatcher changes use a 10% canary for at least ten minutes. Promotion requires stable duplicate ratio, provider error rate, queue age, and worker restart count. Rollback does not delete queued jobs and must preserve Delivery Ledger compatibility.
