# Payment Settlement Processing Delay

Document ID: INC-2025-0061
Department: Payments
Document type: Incident
Access level: Internal
Created date: 2025-05-03

## Executive Summary

On 3 May 2025, settlement processing fell 52 minutes behind schedule after a database statistics refresh selected an inefficient query plan for the settlement-item lookup. Worker threads remained occupied by slow queries, queue age increased, and scheduled merchant reports were delivered late. Customer authorization and account balances remained available.

The incident was classified SEV-2 because settlement completed within the contractual end-of-day window but breached the internal queue-age and reporting objectives.

## Impact

- Processing delay: 52 minutes at maximum
- Settlement instructions delayed: 84,306
- Merchant reports delivered late: 1,248
- Financial loss: none identified
- Incorrect settlement amounts: none identified
- Customer authorization impact: none
- Regulatory reporting impact: none

The incident affected timing only. All delayed instructions retained their original business dates and idempotency keys.

## Detection

The queue-age warning fired when the oldest item reached 15 minutes. Worker CPU was below 50%, which initially suggested insufficient message consumption rather than resource exhaustion. Database active-session monitoring later showed 24 settlement workers waiting on the same lookup query.

## Root Cause

The database statistics refresh changed the estimated cardinality for the settlement-item table. The optimizer selected a full-table scan instead of the expected composite-index lookup. Each query held a settlement worker for several seconds, exhausting worker capacity while leaving CPU and memory apparently healthy.

## Contributing Factors

- The critical query did not have a reviewed plan baseline.
- Queue age had warning alerts but no projected breach alert based on arrival and drain rates.
- The operations dashboard emphasized host utilization and did not show database wait classes.
- Merchant report generation competed for read capacity during settlement recovery.
- The release checklist covered schema changes but not scheduled statistics maintenance.

## Recovery Procedure Used

Database Engineering applied the previously validated execution plan, and Payments Operations paused report generation to reserve capacity for settlement. After query latency normalized, the team increased consumers in two stages and monitored lock waits, replication lag, and downstream acknowledgment rates.

Workers were returned to their normal count only after queue age stayed below five minutes for 20 minutes. A full batch reconciliation compared instruction count, total amount, currency totals, and idempotency keys.

## Follow-up Verification

A replay of 150% of peak batch volume completed in 34 minutes with query latency below 120 milliseconds and maximum queue age below six minutes. Plan-baseline removal and rollback were also tested in staging.
