# Duplicate Payment Notification Incident

Document ID: INC-2025-0074
Department: Customer Experience
Document type: Incident
Access level: Confidential
Created date: 2025-08-11

## Executive Summary

On 11 August 2025, a deployment to the Notification Dispatcher caused duplicate payment-confirmation messages for a subset of mobile banking customers. Payment processing and ledger posting were correct. The defect affected messaging only and did not create duplicate charges.

The deployment changed acknowledgment ordering between the dispatcher and the durable notification queue. Workers sent a message successfully but restarted before recording the delivery acknowledgment. The queue then redelivered the event, and the downstream provider accepted it because the provider request lacked the internal notification idempotency key.

## Impact

- Incident window: 09:16–10:03 UTC
- Duplicate messages sent: 8,912
- Unique customers affected: 4,107
- Maximum duplicates for one event: 3
- Duplicate payments or ledger entries: 0
- Notification delivery objective breached: 17 minutes

Customers received repeated push or SMS confirmations and some believed they had been charged multiple times. Customer Support used a prepared assurance statement after ledger reconciliation confirmed single postings.

## Root Cause

Version 2.8.0 acknowledged queue messages after writing delivery state to a new analytics sink. A transient analytics timeout restarted the worker after the provider accepted the notification but before the queue acknowledgment completed. Redelivery was expected queue behavior, but the provider request did not include the internal event id as an idempotency key.

## Contributing Factors

- The release test used an always-available analytics stub and did not test worker failure after provider acceptance.
- Duplicate-rate alerting used a fixed threshold that was too high for normal daytime volume.
- SMS and push provider adapters implemented idempotency differently.
- The deployment proceeded to 100% of workers without a ten-minute canary observation period.

## Resolution

Operations paused consumers, rolled back to version 2.7.4, and resumed processing in stages. The team did not delete queued events. Instead, the dispatcher checked the delivery ledger before each send and suppressed events already recorded as delivered.

## Corrective Actions

| Action | Owner | Target date | Status |
|---|---|---|---|
| Send the internal event ID as the provider idempotency key | Notification Platform | 2025-08-15 | Completed |
| Acknowledge queue messages independently of analytics writes | Notification Platform | 2025-08-18 | Completed |
| Add failure-injection tests after provider acceptance | Quality Engineering | 2025-08-22 | Completed |
| Alert when duplicate ratio exceeds 0.05% for five minutes | Site Reliability | 2025-08-14 | Completed |
| Require a ten-minute 10% canary for dispatcher releases | Release Engineering | 2025-08-13 | Completed |
